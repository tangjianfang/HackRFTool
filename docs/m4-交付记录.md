## 排障记录（本轮最重要的知识）

1. **CPU 饥饿链**（花费最多的一个 bug 链）：Debug 构建 + `feed()` 每回调 256 次全量 FFT + 每次堆分配 → 回调线程吃满 CPU → libusb 控制传输延迟秒级 → 跳频龟速/UI 冻结/帧率跌至 6%。修复三件套：feed 抽样 4 倍 + 缓冲复用 + **真机一律用 Release 构建**（`cmake --build --preset x64-release`）
2. **绝不在绘制线程同步调 libhackrf**：首帧 build 内 `set_freq` 会永久挂起（跳频必须专职线程）
3. 跳频与取帧顺序：先落段数据再跳频（否则慢构建下 `now-hop>settle` 永不成立，全景拿不到数据）
4. 反复 `taskkill /F` 于流传输中会令设备控制通道进入慢速态，`hackrf_spiflash -R` 恢复
5. PowerShell 5.1 对**无 BOM UTF-8 的 .ps1 按 ANSI 解析**，中文注释可能悄悄毁掉语法——脚本一律纯 ASCII
6. Windows 11 全屏遮挡可能停掉 DComp 帧循环，自动化截图前须激活窗口（Alt 键技巧 + SetForegroundWindow）

## 已知问题

- 状态栏「接收中 2450.0 MHz」为启动时的初始调谐文案，扫描模式下不随跳频更新（真实频率看「扫描 段 x/5 @ …」）——M5 清理
- 跳频瞬间（~30ms 静默窗）丢帧属设计取舍
- 手动锁定监测 bin 在扫描模式下语义是「当前驻留段内跟踪」（见 M2 记录）
- 软件跳频全景每轮约 1 秒，突发短事件（如鼠标单帧）可能漏扫——固件硬件 sweep（hackrf_init_sweep）为后续候选

## 运行方式

```sh
hackrf_spiflash -R
out/build/x64-release/Release/HackRFTool.exe        # 手动：模式切「全频段」再点开始
out/build/x64-release/Release/HackRFTool.exe autos  # 自动：启动即接收+全频段
```
