## 真机验证（Release，LNA/VGA=16/16，2450 MHz）

- 突发总数 400+ / 10 秒；列表 27+ 行实时滚动，时长 0.02-0.11ms（短突发，疑为蓝牙/BLE），hex 预览各行不同
- ESB✓ 标记本次环境未命中（环境信号以 WiFi/蓝牙为主，蓝牙 LE 不是 ESB——预期行为）；识别你的 nRF24 兼容鼠标时会亮起

## 排障记录

1. **时长列恒 100.00ms = 全环连片**：默认增益 32/30 下时域能量整段高于 -40dB 阈值（频谱按 bin 分摊能量看不出饱和——M3 教训重演）。**默认增益改为 16/16**，并在页头加提示「时长接近 100ms 时下调增益」
2. **hex 缺失（第一层）**：`live.refresh()` 原在 build 末尾，行文本滞后一个构建周期生成，突发已被环挤出 → `read_slice` 失败。移到 build 开头 + 环 1M→2M
3. **hex 缺失（第二层）**：全环长度"突发"的 read_slice 必然越界——增益修复后随之解决
4. **scroll_view 视口塌 0**：列布局内视口必须 `flex_grow=1`，否则 0 高度不渲染任何行
5. µs 换算：`样本/(fs/1e6)`，已按 Msps 折算后不能再乘 1e6

## 已知问题

- 三个 tab 汉字标签间距偏挤（WinFlux tabs 组件内部样式，M2 两枚时正常，待上游）
- GFSK 解调固定按 1 Msps 符号率（2 Mbps 设备需切 2e6 参数，暂未做 UI 开关）
- ESB 真实设备兼容性覆盖 2 前导×3 地址长×2 CRC 初值；专有协议（罗技 Unifying 等）不在此列

## 你的鼠标实验（升级版）

1. `HackRFTool.exe` → 频谱页「全频段」找活动频点 → 切单窗对准 → 实时抓包页

3. 或直接 `● 录制 IQ` 落盘 → `HackRFAnalyze 文件.cs8 -40` 离线复查
